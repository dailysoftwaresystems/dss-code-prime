# `artifactProfile` Concept — Sub-Plan

> A first-class concept naming **the shape an output takes** when a language is compiled. The language config declares which profiles it supports; the project config picks one; the driver enforces compatibility. Prevents nonsense like "compile this C source as a UI binary" or "compile this T-SQL as a shared library."
>
> **Naming.** The chosen field name is `artifactProfile`:
> - *artifact* — what the compiler produces (binary, library, script, etc.). Avoids overloading "target" which already means CPU/OS.
> - *profile* — a named configuration that constrains downstream toolchain behavior, in the same sense as `BuildProfile` in modern build systems.
> - Reads naturally: `"artifactProfile": "cli"`, `"artifactProfiles": ["cli", "lib"]`.

## 1. Motivation

Compiling a language means **something different per language × per consumer**. Today the project has no way to say:

- "C-subset can produce a CLI binary OR a shared library, but never a GUI bundle."
- "T-SQL doesn't produce a native binary at all — its sensible outputs are a stored-procedure deployment script or an inline embedded statement."
- "Toy is a teaching language — only the CLI profile makes sense."

Without this constraint, a user can author a project that asks for a profile the language can't legitimately produce, and the failure surfaces deep in codegen (or worse, produces a broken artifact). The check belongs at config-load time.

`artifactProfile` is also the right home for **profile-specific codegen knobs** — entry-point name (`main` vs `WinMain` vs `DllMain`), subsystem flag (PE), startup runtime (CRT vs minimal), default linker flags. The language config declares what's allowed; the project config selects; codegen reads both.

## 2. Design

### 2.1 Language config field (`*.lang.json`)

```jsonc
{
  "dssSchemaVersion": 2,
  "language": { "name": "c-subset", "version": "0.1.0", "fileExtensions": [".c", ".h"] },

  "artifactProfiles": ["cli", "lib"],   // ← NEW: list of valid profile names this language supports

  "tokens":  { /* ... */ },
  "shapes":  { /* ... */ }
}
```

- **Required** for `dssSchemaVersion >= 3` (new bump). For v2 configs the field is optional; absence is treated as `["cli"]` for backward compatibility with toy/c-subset, and as `["script"]` for SQL-shaped languages (heuristic: language declares a `reservedWordPolicy: "contextual"` AND no `main`-anchored shape).
- Loader emits `C_MissingField` if `dssSchemaVersion >= 3` and the field is absent or empty.
- Each entry must be a recognized profile name (see §3). Unknown entries → `C_UnknownArtifactProfile`.
- Duplicate entries → `C_RedundantField` (warning, dedup silently).

### 2.2 Project config (TBD — new file format)

The "project config" is a per-source-tree `.dss-project.json` (or similar) that points the driver at:
- The language to use (resolves to a `.lang.json`)
- The source files to compile
- The desired artifact profile
- Codegen knobs (target triple, optimization level, output path)

```jsonc
{
  "language":        "c-subset",
  "artifactProfile": "cli",                // ← NEW: must be ∈ language's artifactProfiles
  "targets":         ["linux-x86_64", "win-x86_64", "macos-arm64"],
  "sources":         ["src/**/*.c"],
  "output":          "dist/myprog"
}
```

The project-config file format is itself a v1 deliverable — see `00-compiler-implementation-plan - tbd.md` §4.1 (the `program/` driver layer) and the production-readiness plan.

### 2.3 Driver enforcement

At project-load time, the driver:

1. Loads the language config; reads `artifactProfiles`.
2. Loads the project config; reads `artifactProfile`.
3. Asserts `project.artifactProfile ∈ language.artifactProfiles`. Mismatch → fatal `D_ArtifactProfileNotSupported` (driver-phase diagnostic, new `D_*` code namespace alongside `P_*` and `C_*`).
4. Stamps the resolved profile onto the `CompilationContext` (or equivalent) so every downstream phase can read it without re-walking configs.
5. Stamps the **entry-point selection** (which source file is the artifact's entry, read from the project config) onto the same `CompilationContext`, beside the profile. This is the home for the entry-point decision — the `CompilationUnit` stays entry-agnostic ([`08-compilation-unit-plan`](./08-compilation-unit-plan%20-%20tbd.md) §2.6 C2-D2 re-routes it here from the CU layer). Codegen (§2.4) reads the entry source + the profile-derived entry-point *symbol* name together.

### 2.4 Codegen consumption

> **Config-driven, not hardcoded per profile (thesis decision #4).** The mappings below are **defaults/derivations the codegen computes from config**, not a hardwired `if (profile == "gui")` ladder. The entry-point *symbol convention* is **declared by the language config** (the language config declares the convention — e.g. a `main`-named symbol, or whichever symbol the language's own `semantics` block / per-target overrides indicate) with **per-target overrides**; the profile + target supply the subsystem/extension/runtime knobs. Codegen branches on the **target** axis (PE vs ELF vs Mach-O — expected) and reads language/profile **config**, never on `schema.name()`. A new language picks its entry convention in config, not by editing codegen.

`gen/link` resolves, from the language config + selected profile + target:
- The entry-point symbol — sourced from the language config's declared entry convention (default `main`), with target overrides (e.g. `gui`+PE → `WinMain`/`wWinMain`; `lib`+PE → `DllMain`; ELF `_init`/`_fini`; Mach-O `__attribute__((constructor))` registration).
- The PE subsystem field (`IMAGE_SUBSYSTEM_WINDOWS_CUI` vs `IMAGE_SUBSYSTEM_WINDOWS_GUI` vs the DLL flag) — from profile × target.
- The output file extension (`.exe` / `.dll` / `.so` / `.dylib` / no-extension) — from profile × target.
- Pick the linker default-library set (CRT for CLI/GUI, none for freestanding libraries).

For T-SQL-style languages (`script`, `sproc`), "codegen" is a text-emission phase, not a native-binary phase — the driver picks an entirely different backend variant.

## 3. Profile vocabulary — registered set

> **Updated 2026-05-23** per the universal-compiler decisions in [`00-master`](./00-compiler-implementation-plan%20-%20tbd.md) §1 (rev 2). The vocabulary is no longer a compile-time enum; it's a **registered set** owned by the loader and contributable by each shipped backend plan. New profiles arrive via the schema-version bump that introduces their backend, not via config-level name invention.

> **Updated 2026-08-12 (AP5) — the set became a TABLE.** Each row now carries a **composition verb** beside the name: `DependencyComposition ∈ {SourceMerge, ArtifactLink, NotConsumable}`, declaring how an artifact built under that profile folds into a **consumer's** build when it is named in `dependsOn`. ★ **THE ENGINE SWITCHES ON THE VERB, NEVER THE PROFILE NAME.** The naive spelling of the `dependsOn` composition fork is `if (profile == "module") … else if (profile == "staticlib" || profile == "lib") … else fail` — the exact identity branch this vocabulary has always vetoed, and one that goes *silently* wrong for the eleventh profile (it lands in the `else`, and whether that is correct is an accident of which arm the author wrote last). Putting the answer in the row means an eleventh profile that composes like `staticlib` is ONE row spelling `ArtifactLink`: the fork grows no arm, no call site is revisited, and no site can forget the new name. A genuinely novel composition is the only thing that may add an **enumerator** — and then the compiler's exhaustiveness warning walks the author to every switch that must answer for it, which a string compare never would. `dependencyCompositionForProfile()` returns `std::nullopt` for an UNREGISTERED name, which is deliberately not interchangeable with `NotConsumable`: every enumerator is a valid *instruction*, `NotConsumable` included ("reject — the profile is terminal"), so a typo (`"modul"`) must produce an unknown-NAME diagnostic, not a "profile cannot be a dependency" complaint about a name that does not exist.

**Loader behavior.** The loader holds a **registered profile set** — as built, the `kRegisteredArtifactProfiles` table in `core/types/artifact_profile.hpp`, shared by the grammar loader (which profiles a language SUPPORTS) and the object-format loader (which a format SERVES); both reject an unregistered entry at load time (`C_UnknownArtifactProfile`). ⚠ The `ArtifactProfileRegistry::registerProfile` startup-registration call in this paragraph's original text was never built and is **not** how it works: adding a profile is a **row** in that table, in a change that also ships its backend. **ORDER IS LOAD-BEARING** — `registeredArtifactProfileList()` derives the human-readable diagnostic list from the table in place, so a new profile is **APPENDED**; reordering silently rewrites every "registered profiles: …" message a user has ever been shown. The count is deliberately **not** written here (this paragraph used to say "the eight names above" while the table listed nine); read the table.

**Diagnostics.**
- `C_UnknownArtifactProfile` — profile not in the registered set at load time.
- `C_ProfileBackendMissing` (new) — profile registered but its backend (per the plan table above) isn't compiled into this build. Allows partial builds (e.g. shader-less dev builds) to fail-loud rather than silently strip output.

## 5.1 §B — DECISIONS OF RECORD for AP6 (`dependsOn` resolution)

> ★ **These are OPERATOR DECISIONS ALREADY MADE (2026-08-12). They are recorded here so AP6 implements them rather than re-litigating them.** Two questions are genuinely still open and are marked as such at the end — those, and only those, are the implementer's to bring back.

**B.1 — Entry shape and the `path` contract.** A `dependsOn` entry is `{path}` **XOR** `{git, ref}`; this half already ships (AP5 (d)). AP6 adds: a **`path` dependency must have a `.dss-project.json` at its root, or fail loud** — `D_DependencyManifestNotFound` (0xD019), which is remediation-distinct from `D_FileNotFound` precisely because the overwhelmingly common cause is a wrong-*level* path (`../lib/src` for `../lib`). Name both the manifest looked for and the absolute path looked at.

**B.2 — Composition is HYBRID, dispatched on the DEPENDENCY'S OWN `artifactProfile` through the composition verb (§3).** Never on the profile NAME, never on the consumer's profile:

| Dependency's verb | Profiles | What AP6 does |
|---|---|---|
| `SourceMerge` | `module` | Merge the dependency's expanded sources into the consumer's compilation. **Same `language` required** — merged sources are parsed by the CONSUMER's grammar, so a mismatch is a guaranteed parse failure and must reject at resolve time (`D_DependencyLanguageMismatch`, 0xD01C) rather than surface as a pile of `P_UnexpectedToken` in a file the user never wrote. |
| `ArtifactLink` | `staticlib`, `lib` | **Build the dependency to its own artifact, then thread that artifact into the consumer's `resolveLibraries`.** The two builds stay separate. This arm makes **no** language claim — cross-language linking against a built artifact is the entire point of the FFI surface and must stay legal. |
| `NotConsumable` | everything else | **Fail loud** (`D_DependencyArtifactProfileUnsupported`, 0xD01B). Absorbing a `cli` dependency as sources would splice its `main()` into the consumer, and "linking" one is not a thing the profile can offer. Fail **CLOSED** on an unrecognized/absent profile — but report the unknown NAME (`C_UnknownArtifactProfile` + `registeredArtifactProfileList()`), never the terminal-profile complaint. |

**B.3 — Base-dir rule (two different answers, and that is correct).** The **ROOT** manifest resolves its relative paths against the **process cwd** — existing shipped behavior for `sources[]` globs (`docs/project-config-spec.md` §2.1), **do not change it**. A **DEPENDENCY** manifest resolves against **its own directory**. Anything else makes a dependency's meaning depend on where the depender happened to be invoked from. The runner already anticipates this: `runBuildScripts` takes `cwd` as a parameter, so a dependency's codegen hook runs in the dependency's tree without a caller-kind branch.

**B.4 — `.dss-deps` CACHING. ★ NEWLY DECIDED 2026-08-12, AND IT SUPERSEDES THE EARLIER "FETCH ON EVERY BUILD" INSTRUCTION.** Builds are **reproducible and offline-by-default**:

- ★ **WHERE `.dss-deps/` LIVES — operator-clarified 2026-08-12, and it is a correctness rule, not a convention.** The cache is created **in the CONSUMING project's own directory, beside that project's `.dss-project.json`** — i.e. in the *user's* repo, the one being compiled. It is **never** created inside the dss-code-prime repo, and never in a shared/global/user-home location. Two consequences the resolver must honour: a build of someone else's project must not write a byte into the compiler's tree, and **two different consuming projects that name the same git URL each get their own checkout** — the cache is per-project, so it is never a cross-project shared mutable store whose contents depend on what somebody else built last. (Sharing would be a *deduplication* feature with its own invalidation and concurrency design; it is explicitly not what this is.) The reason `.dss-deps/` also appears in **this** repo's `.gitignore` is only that this repo contains manifests of its own under `examples/` and `real-examples/`.
- Each dependency records `{url, ref, resolvedCommit}` as **cache state** beside its `.dss-deps/<name>/` checkout.
- **CACHE HIT** — a checkout exists and its `HEAD` matches the recorded `resolvedCommit` for that `(url, ref)` ⇒ the build performs **NO NETWORK ACCESS AT ALL**. Not a conditional request, not a `ls-remote`, nothing.
- **MISS** ⇒ clone/fetch, resolve the ref to a commit, check out, record.
- **NETWORK FAILURE WITH an existing checkout** ⇒ `D_DependencyGitFetchFallback` (0xD01F) at **Info** severity, and **the build PROCEEDS** on the checkout it has.
- **NETWORK FAILURE with NO checkout** ⇒ **fail loud** (`D_DependencyGitAcquireFailed`, 0xD01E). The discriminator between 0xD01E and 0xD01F is *exactly* "is there a usable checkout" — never the git exit status or the operation name (clone vs fetch), or an offline build's outcome would depend on how git happened to phrase the failure.
- A **moving ref (a branch)** refreshes only under an explicit opt-in flag, **named by the operator 2026-08-12: `--force-git-cache` on the `build` command**, which *forces the pull*. ⚠ **AMENDED BY B.11 (2026-08-14): there is no `build` subcommand** — ✔MEASURED against `src/program/cli_args.cpp` (modes are flags; a bare positional is rejected), so it lands as a **global** flag. The flag NAME and every other clause of this bullet are unchanged; only the surface it attaches to was wrong, because it was written before the CLI was re-read. Without it a branch dependency is as reproducible as a tag: you get the commit you got last time. The flag bypasses the cache-hit short-circuit only — every other rule above (fallback-on-network-failure, fail-loud-with-no-checkout) is unchanged by it, so `--force-git-cache` on an offline machine with an existing checkout still emits 0xD01F and still builds.
  ⚠ *Implementer's note, not a re-litigation:* the name reads naturally as "force **use of** the cache" while it means "force **refresh of** the cache". The operator chose it; ship it. Mitigate in `--help` with an imperative gloss ("re-fetch git dependencies even when the cache is valid"), not by renaming.
- `.dss-deps/` is git-ignored (`.gitignore`, beside `target/`).

  **★ WHY 0xD01F IS `Info` AND NOT `Warning` — write this down, because "tidying" it is a one-line regression of the whole offline guarantee.** ✔MEASURED at `src/core/types/diagnostic_reporter.cpp:120-122`: `if (cfg_.policy.warningsAsErrors && d.severity == DiagnosticSeverity::Warning) d.severity = DiagnosticSeverity::Error;` — the promotion is **code-agnostic**, with no per-code exemption anywhere in the codebase, and membership in `kUnsuppressableCodes` explicitly does **not** exempt a code from it (that table gates *silencing* only). At Warning, every project built with `--warnings-as-errors` would therefore **fail the moment the network did** — the exact outcome the code exists to prevent. `--suppress` is the wrong instrument in the other direction: it silences the staleness notice rather than preserving the build. Info is not promoted by that arm, does not count toward `errorCount()`, and is still visible at default verbosity (`drainDiagnosticsToStderr` renders every diagnostic with no severity filter, and the CLI has no `--quiet`/`--verbose`). ⚠ This also **constrains how `D-FF2-UNSUPP-INFO-WAE-ASYMMETRY` may be closed** — "extend the elevation gate to also promote Info" would regress this; the anchor's docblock in `unsuppressable_codes.hpp` now names 0xD01F as its live consumer.

**B.9 — ★★ DELIVERY IS NOT SUPPRESSION. The motivating problem — a build exceeding `maxDiagnostics` silently dropping a must-see notice — is a **DELIVERY** concern. Joining the table to get delivery uses membership as a side-channel for a property it was never defined to carry, and pays for it by loosening the table's one criterion. ⓘ The file already records the discipline this would break: at 139→141 **two** of three inline-asm codes joined and `S_InlineAsmDuplicateQualifier` deliberately did **not**, the comment calling that 2-of-3 split *"evidence the criterion was applied rather than the codes swept in as a batch"*. ⇒ **THE ORDER IS FIXED: (1)** make the cap incapable of silent truncation — it must state HOW MANY were elided and how to raise the limit (✔MEASURED on this branch: `diagnostic_reporter.cpp:222-234` already emits a `P_TooManyDiagnostics` marker naming the limit, but gives **no count** because `hitCap_` short-circuits at `:207` without tallying, and names **no flag** because ✔MEASURED no `--max-diagnostics` flag exists); **(2)** give DELIVERY its own property **bound to the diagnostic, NOT to a second code list** — *"a second table listing codes is a second source of truth about diagnostics; the hand-maintained size literal is the tell"* — and no `D_Dependency`-specific escape, since whatever guarantees delivery must be what every phase's codes use; **(3)** only then decide membership **code by code**, four separate verdicts against the written criterion, each with its own rationale block. ⚠ **AND THE SAME ERROR IS ALREADY COMMITTED:** `D_ScriptSpawnFailed`/`D_ScriptExitedNonZero` were added to the table earlier the same day with a rationale block that cites cap-immunity as half its argument. **B.10 — ★★ U-2 IS AMENDED: CONSUMER-DRIVEN DERIVATION, NOT A SUPERSET CHECK. Operator decision 2026-08-14, taken during the AP6 cycle after an independent design audit returned DO NOT PROCEED on U-2 as written.**

✔**THE MEASUREMENT THAT KILLED THE ORIGINAL RULE — it is not hard, it is impossible.** Object-format served-profile sets are **pairwise disjoint**: `cli` 7 formats, `lib` 5, `staticlib` 5, and 7 serve none (measured over all 24 `src/dss-config/object-formats/*.format.json`). `Program::compileProject` enforces `profile ∈ format.artifactProfiles()` on **every** entry of `targets[]` (`src/program/program.cpp:2053-2064`). Therefore a `cli` consumer's specs are always `…-exec`/`…-pie` and a `staticlib` dependency's are always `…-staticlib`, and the two lists **can never share a spec string**. U-2's *"require the dependency's `targets[]` to be a superset of the consumer's"* would have fired `D_DependencyTargetNotBuilt` on **every legitimate ArtifactLink edge**, including the corpus example B.6.2 mandates — a dead arm whose own test would have gone green on the reject.

**THE RULING.** Build the dependency for the platforms the **CONSUMER** declares. A dependency's own `targets[]` is **NOT consulted** when it is built as a dependency; it still governs a standalone build of that project.

★ **THE REASON, WHICH IS THE DESIGN PRINCIPLE AND NOT JUST A VERDICT — operator, 2026-08-14:** `targets[]` is *the platforms a project builds for itself*. *"Which platforms this code can support"* is a **different statement**. Conflating them produces a specific defect: a dependency whose source is perfectly portable, but whose manifest simply has not listed arm64, rejects an arm64 consumer. **The tool refuses work that would have succeeded**, with a message that reads as a capability claim while actually reporting a bookkeeping gap — a FALSE NEGATIVE with a confidently misleading diagnostic, which sends the reader to the wrong place. A list that must be kept in sync with your consumers' platforms is exactly the hand-maintained enumeration this config model exists to remove, and drift in it is silent until it produces the wrong reject. ⚠ **Weigh the two failure modes honestly:** the superset rule fails EARLY, WRONGLY and MISLEADINGLY on a portable dependency; derivation fails LATE, CORRECTLY and PRECISELY — a dependency that genuinely cannot serve a platform produces a compile error inside itself, pointing at the actual unsupported construct. **A late true negative beats an early false one.** Neither is silent, so the fail-loud bar does not decide this; the diagnostic's TRUTHFULNESS does.

**THE DERIVATION.** For each consumer target spec `<targetName>:<consumerFormat>`, the dependency's object format is the **unique** F satisfying all three: (1) `F.format.kind == consumerFormat.format.kind` (`elf`/`pe`/`macho`, a declared field); (2) `dependency.artifactProfile ∈ F.artifactProfiles()`; (3) `crossValidateTargetFormat(target, F)` passes — the EXISTING validator at `src/program/cross_validate_target_format.hpp:52`, never a parallel one. No format-name parsing anywhere; the relation is read from declared config only, and it **fails closed** on zero or ≥2 candidates.

**DIAGNOSTICS.** `D_DependencyTargetNotBuilt` is **never minted** — ✔MEASURED the slot was still free (highest allocated was `D_SuppressRequestIgnored = 0xD021`, `parse_diagnostic.hpp:1869`), so nothing is retired and the *semantic* is simply dropped. A code that can only fire on a bookkeeping gap is the same category as the five members the 144→139 shrink removed from `kUnsuppressableCodes` for asserting nothing while reading as load-bearing. The free slots take the two facts the derivation can actually produce, plus U-5's renumbered code: `D_DependencyTargetFormatUnresolvable = 0xD022` (**zero** candidates — names the target, the dependency's profile and the format kind), `D_DependencyTargetFormatAmbiguous = 0xD023` (**≥2** candidates — names the target and every candidate; never a silent first-match), `D_DependencyDerivedNameInvalid = 0xD024`.

⛔ **SCOPE — SHIP THE DERIVATION ONLY.** The ability for a dependency to DECLINE a platform is designed here and **deliberately not built**: no shipped dependency needs it, and building a mechanism with no consumer is the no-workaround violation in the other direction that §A.2 names. It is anchored trigger-gated as **[[D-DEPS-DEPENDENCY-CANNOT-DECLINE-A-TARGET]]** — when it fires, the fix is a declared **CONSTRAINT** (not a target list) on axes config already carries (`format.kind` / `container` / artifact profile), checked through `crossValidateTargetFormat`, modelled on `D_DependencyArtifactProfileUnsupported` (0xD01B, `parse_diagnostic.hpp:1723`), which is already exactly this pattern: a declared fact producing a clean resolve-time reject. **ABSENT constraint ⇒ build whatever is asked** (zero bookkeeping in the common case ⇒ no drift, no false negatives); PRESENT constraint ⇒ clean reject naming the axis and the reason. **Do NOT build before the trigger fires.**

☆ **A CONSEQUENCE WORTH WRITING DOWN, because it makes AP6 smaller rather than larger:** since the RESOLVER is now the only producer of per-target libraries, **no user-facing per-target `resolveLibraries` vocabulary is added at all** — not to the manifest, not to the CLI. Both stay program-wide and their existing merge semantics are untouched. U-2's "make it per-target" is satisfied by an INTERNAL channel on `runCusToTargets`, index-parallel to `targets` exactly like the existing `grammarPerTarget`/`keyPerTarget`, merged at `program.cpp:1756`. A user-facing per-target declaration would be a mechanism with no consumer.

**THE SIX TESTS THIS DECISION REQUIRES** (each proven red-on-disable by reverting the fix, not merely by passing): (1) a consumer targeting **arm64** with a dependency whose manifest lists **only x86_64** resolves and builds — the case the rejected option refuses, and the whole point of the decision; (2) the derived format is the unique one for the consumer's target and the DEPENDENCY's profile — assert the **exact resolved format string**, not just success (staticlib-under-exec is canonical); (3) non-uniqueness FAILS CLOSED naming the target and the candidates; (4) a consumer target with no compatible format rejects at resolve time naming the axis — **pin the message**, not just the rejection; (5) `0xD01B` still fires on a genuine profile mismatch, proving the derivation did not swallow a reject that already worked; (6) no test references the retired `D_DependencyTargetNotBuilt` semantic, and the emit-site guard is green.

**B.12 (withdrawn) — `targets[]` IS DERIVED FROM THE FORMAT TABLE, NOT FROM THE COMPOSITION VERB.** The proposal was REJECTED **as worded** while its OUTCOME was kept: a `module` manifest stops declaring `targets[]`.

**WHY THE VERB IS THE WRONG AXIS — the file says so in its own words.** `artifact_profile.hpp:64-66` defines `DependencyComposition` as *"how an artifact built under a given profile composes into a CONSUMER's build WHEN IT IS NAMED AS A DEPENDENCY (`dependsOn`). This is the only per-profile axis the engine is permitted to switch on."* That is a **CONSUMER-SIDE** axis. `targets[]` is a **PRODUCER-SIDE** question — for which targets is THIS project's own build product emitted — and has nothing to do with `dependsOn`. ✔The two axes are already NOT parallel in the shipped table: `NotConsumable` covers `cli`/`gui`/`script`/`sproc`/`transpile`/`shader`/`hdl`, which `:77-78` says *"produce a TERMINAL deliverable"* — they DO produce artifacts and merely cannot be depended upon. **THE RULE — DERIVE IT, DO NOT DECLARE IT.** The **union of `format.artifactProfiles()` over the shipped object formats IS the set of profiles that can produce a build product.** That table is already config, already authoritative, and is already the AP3 gate's own predicate (`program.cpp`: `profile ∈ format.artifactProfiles()`, *"the same generic predicate, no per-profile-name / format-identity branch"*). Ship it **BIDIRECTIONALLY** — "optional" is the weak half and leaves the field able to lie in the other direction:
- served by **≥1** shipped format ⇒ `targets[]` REQUIRED and non-empty (unchanged today);
- served by **ZERO** shipped formats ⇒ declaring `targets[]` is an ERROR naming the profile and the fact that no format serves it.

★ **WHAT DERIVATION BUYS THAT A DECLARED RULE DOES NOT:** zero new keys, enumerators or tables; it is **SELF-MAINTAINING** (the day a format legitimately serves `module`, or a new no-artifact profile ships, the rule flips automatically and correctly); and it makes the rejected "just add `module` to some format's `artifactProfiles[]`" option **SELF-DEFEATING rather than merely wrong** — doing so immediately makes `targets[]` REQUIRED again, so it cannot be smuggled in later as a quiet fix without visibly re-breaking what it claims to fix.

Split them from the same table — served by ≥1 format but not THIS one ⇒ genuine mismatch, naming the formats that DO serve it; served by ZERO ⇒ a distinct diagnostic, *"profile `module` produces no build product; it is absorbed into a consumer via SourceMerge and cannot be built standalone."* ★ That second message is where the composition verb finally earns its place — answering a consumer-side question, which is what it is for.

A hardcoded `if (profile == "module")` or `if (verb == SourceMerge)` passes every other test in the list and **FAILS this one**. Also pin: a module manifest WITH `targets[]` ⇒ the new error; WITHOUT ⇒ clean; a `cli`/`lib` manifest WITHOUT `targets[]` ⇒ still an error (proving the requirement was made CONDITIONAL, not deleted); and the standalone-module diagnostic asserted on its **TEXT**, not merely its code.

**MIGRATION.** AP6's SourceMerge corpus example DROPS its `targets[]` **and its explanatory comment** — that deletion is the deliverable proving the manifest stopped lying. ⚠ If the comment survives, the fix did not land.

⛔ **SCOPE: this is NOT in the AP6 commit.** Seven profiles, a driver gate, a new diagnostic and an `ArtifactProfileMatrix` rewrite are their own cycle, and AP6 is already the largest since AP5. The operator's instruction was *"I want everything fixed. If too big in this cycle, split in more dss-cycle. BUT DO IT"* — so this is the **NEXT** cycle's priority, recorded here in full so it is implemented rather than re-derived. Until it lands, the corpus example keeps its `targets[]` and the comment explaining why.

**B.13 — ★★ THE PROFILE/COMPOSITION SPLIT, AND WHAT A `module` ACTUALLY IS. Operator rulings 2026-08-15, taken in sequence during the AP6 close-out. These SUPERSEDE B.12-CORRECTED's `emitsArtifact` design, which is WITHDRAWN.**

**B.13.1 — TWO ORTHOGONAL FACTS THAT B.12 CONFLATED.** `artifactProfile` answers *"what do I build MYSELF as"*; `DependencyComposition` answers *"how am I CONSUMED"*. They never needed to interact, and tying them together is what made B.12 wrong.

**B.13.2 — ⛔ `emitsArtifact` IS WITHDRAWN. Do not build it, do not re-propose it.** B.12-CORRECTED introduced a `bool emitsArtifact` column on `ArtifactProfileRow` (false for `module`) making a declared `targets[]` a LOAD ERROR for such a profile. ✔**The operator's objection is decisive: a `module` project you cannot build standalone is one you cannot type-check, cannot codegen, cannot run a corpus example against, and cannot get a diagnostic from — until some consumer imports it, at which point its errors surface INSIDE THE CONSUMER'S BUILD, attributed to the consumer.** That is precisely the failure shape B.10 and B.12 exist to prevent, reproduced one level down. ★ And the sharper form: **compiling a module REQUIRES a target even though it contributes no artifact to a consumer** — codegen is target-specific, so `targets[]` on a module is not bookkeeping, it is the INPUT to the only build that project can have. Forbidding it forbids the compile. ⇒ the column had no honest reader and was deleted; the corpus example's `targets[]` and its explanatory comment were RESTORED.

**B.13.3 — ★ A `module` IS A LIBRARY.** ✔Operator, 2026-08-15: *"a module is a lib, essentially, just used via code"* and *"lib in format, like `.a`, `.so`, `.dll`, `.dylib`, etc… can be static or not, like we already do."* ⇒ `module` is served by the library formats in **BOTH flavours** — every format that already serves `lib` **or** `staticlib`. **The static-vs-dynamic choice is ALREADY expressed by the `<targetName>:<formatName>` spec the author writes in `targets[]`**: a module wanting an archive names a `-staticlib` format, one wanting a shared library names `-dyn`/`-dylib`/`-dll`. The profile says *"I am a library"*; the target spec says *"in which container"* — exactly how `lib` and `staticlib` already behave. ⇒ the existing AP3 gate (`profile ∈ format.artifactProfiles()`) passes for a standalone module build with **ZERO new engine code**; this is a config edit.
⚠ **THIS OVERTURNS A PREMISE STATED IN AP5**, which said `module` is *"served by no object format because it is a dependency-side profile ⚠ **PREMISE OVERTURNED 2026-08-15 — see plan-06 §5.1 B.13.3: a `module` IS a library. It builds STANDALONE (targets, serving format, artifact) and is served by the library formats in BOTH flavours (every format serving `lib` or `staticlib`); only its CONSUMPTION is source-merge, and a consumer ignores its artifact entirely. The `emitsArtifact` design B.12-CORRECTED proposed to express this is WITHDRAWN.**."* That is now WRONG: a module is not dependency-side, it is a **library whose CONSUMPTION happens to be source-merge**.

**B.13.4 — WHAT CROSSES THE BOUNDARY, AND WHAT IS IGNORED.** ✔A dependency's own `targets[]` is not *ignored in general* — it is ignored **in that role**. It still governs a **STANDALONE** build of that project. Built as a dependency, the **ROOT's targets drive the entire graph**, root-down, nested chains included. For a `SourceMerge` (`module`) dependency **nothing about its own build is consulted at all** — not its format, not its targets, not its artifact — only its SOURCES, which are then compiled for the CONSUMER's target. ⇒ a module's `targets[]` cannot affect a consumer, and a module declaring only an x86 target merges perfectly into an arm64 consumer, because what crosses the boundary is source, not a binary.

**B.13.5 — THE ONE EXCEPTION, AND IT IS NOW DECLARED CONFIG: ISA BINDING.** ✔Operator: *"if I'm importing a project written in x86 assembly, my root project must have an x86 target only, otherwise this will fail, because x86 assembly only runs in x86, it's not portable."* Generalized: **some source languages are inherently bound to an instruction-set architecture; most are portable.** A new `isa` axis is declared on BOTH sides and compared **by equality only** — `target.isa` (`x86_64` / **`aarch64`**) and a **top-level** `isa` on the language document (`asm-x86_64-att` → `x86_64`, `asm-arm64-gas` → `aarch64`; ABSENT on `c-subset`/`toy`/`tsql-subset`/`asm` ⇒ **portable, always builds**).
★ **Why this is NOT the per-dependency target enumeration rejected 2026-08-14:** an assembly dialect's architecture is **definitional, not a build list**. A new `x86_64-v3` target declaring `isa: "x86_64"` satisfies an existing binding with **no edit to any language config and no C++ change**. The rejected design required editing every dependency when a target was added; this requires editing nothing.
★ **Why `aarch64` and not `arm64`:** it is ARM's own psABI name, and it makes `isa ≠ name` on a **SHIPPED** target — so a name-keyed impostor cannot reproduce the shipped verdicts without inventing a mapping table. The config-driven property is visible in production config, not only in a fixture.
✔MEASURED before minting it (§A.1b): **nothing in the pipeline carried a declared ISA identity.** `format.kind` cannot separate arches (both ELF arches are `kind: "elf"`); `abiModel` is `register-machine` on both; `dataModel` is identical across them; `runOn` is HOST and forbidden for build decisions; `defaultAssemblyLanguage` records a DEFAULT, not a capability, and deriving from it repeats what B.12-CORRECTED withdrew; `shippedLibs`' `when.arch` resolves against `target.name()` and is an identity alias. ✔The shipped format inventory does not even agree with itself on spelling (`elf64-aarch64-*` vs `macho64-arm64-*`), which rules out parsing an arch out of any name.

**B.13.6 — THE COMPLETE PICTURE, so the three mechanisms are not re-litigated as one.**

| Case | Behaviour |
|---|---|
| Portable dependency, any root target | **Builds.** No declaration, no bookkeeping, no drift. |
| ISA-bound language, mismatched target | **Early clean reject** naming both ISAs (B.13.5). |
| Anything else that genuinely cannot build | **Build fails, attributed at the dependency edge** — every inner diagnostic carries `[dependency=<name> target=<spec>]` and the resolver names the manifest, the consumer target and the derived spec. |

⇒ This is why `[[D-DEPS-DEPENDENCY-CANNOT-DECLINE-A-TARGET]]` is **CLOSED BY DECISION**: the declared-capability mechanism it contemplated is needed for exactly ONE axis (ISA), that axis is now declared config, and every other case is answered by the build outcome — which cannot drift and cannot produce a false negative, because it only fires when a build genuinely failed.

**B.13.7 — ⛔ A KNOWN GAP, NOT YET FIXED.** The dependency-edge attribution above covers the `ArtifactLink` arm only. A `SourceMerge` module has **no separate build to wrap**, so its sources compile inside the CONSUMER's compilation and any diagnostic they raise arrives with **no dependency prefix** — the user sees compile errors in files they did not write, in the middle of their own build. ✔The file paths do point into the module's directory, so it is traceable, but it is not labelled, and it is the ONLY arm where a dependency's failure is unattributed. 📄**The fix is the mechanism that already exists, applied per-FILE instead of per-BUILD:** the resolver already knows which merged paths came from which dependency and currently discards that provenance — keep a path→project map and stamp the same prefix (`[dependency=scalemod] scale.c:14: error: …`). Tracked in the registry; not built at the time of writing.

**★ Two rules for the resolver, each discovered by measurement and each now carrying its own registry row.** (1) **Run the consumability gate (0xD01B) BEFORE the format derivation** — ✔MEASURED `(elf, cli, x86_64)` has TWO qualifying formats (`…-exec` and `…-pie`) and uniqueness holds ONLY because `cli` is `NotConsumable` and 0xD01B rejects first; reorder them and 0xD023 becomes genuinely reachable for the commonest profile in the repo (`[[D-AP6-DERIVATION-MUST-RUN-AFTER-CONSUMABILITY-GATE]]`). (2) **Probe `crossValidateTargetFormat` on a throwaway scratch reporter** — it is a REPORTER, not a predicate, so filtering candidates with the live reporter prints a mismatch line per rejected candidate and buries 0xD022 in noise it generated itself (`[[D-AP6-CROSSVALIDATE-AS-FILTER-LEAKS-MISMATCH-DIAGNOSTICS]]`).
