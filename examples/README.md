Curated source programs the DSS compiler must compile + run end-to-end. Each example sits under `<language>/<name>/` and ships:

- a source file (`main.<ext>`) — or several, via a `sources` array for the multi-CU cases (<!--census:examples:top.sources-->32 examples today) — or, in PROJECT MODE, a `.dss-project.json` named by the manifest's `project` key, which owns the input list instead (<!--census:examples:top.project-->6 examples today): its own `sources` may name committed files, or name only a pattern nothing matches until a `preBuildScripts` hook has written it
- a manifest (`expected.json`) declaring the target spec + expected exit code
- optionally, whole SUBDIRECTORIES — an example is a directory TREE, not a flat list of files. Both runners stage the example's neighbourhood into their scratch dir RECURSIVELY, relative subpaths intact, so a dependency that is itself a project (`<example>/dep_module/.dss-project.json` plus its sources, two or more levels deep) arrives whole and an intentionally EMPTY directory arrives too. Only the TOP-LEVEL `expected.json` is withheld — it is the harness's own input, and a scratch copy of it would shadow the file the runner actually parsed — so a file of that name *inside* a subdirectory is the example's own data and IS staged. *2 examples ship a subdirectory today across the corpus — `project_dependson_module_source_merge` (`scalemod/`) and `project_dependson_staticlib_artifact_link` (`foldlib/`), the two corpus witnesses for the compiler's `dependsOn` resolution, each of which nests a whole second project one level down. The capability is ALSO pinned by fixture (`StagesNestedSubdirectoriesWithContentIntact`, and the same self-test inside `integrated_tests`) and both pins are kept: the fixture was added the cycle a nested dependency was silently dropped whole and reported as a missing MANIFEST, and it reds host-independently even when no corpus entry happens to exercise the shape.*

**Two runners drive the same corpus, and a capability must land in BOTH:**

- `tests/examples/examples_runner.cpp` — **in-process**, via `Program::compileFiles` (the API + library link path).
- `integrated_tests/runner.cpp` — **CLI subprocess**, driving the built `dsscp` binary (argv parsing, exit codes, filesystem layout, output routing).

One runner enforcing something its sibling shrugs at is a silent harness bug, not a shortcut — that is how a cross-arch arm that produced NO verdict at all, skipped for want of an emulator and counted as a pass, survived in both for as long as it did. They already share their skip vocabulary, strict parse and emulator lint through `tests/test_support/arm_verdict_ledger.hpp`, and their recursive neighbour staging — plus its self-test — through `tests/test_support/stage_tree.hpp`.

**The run gate is `runOn`, then `emulator` — not "the exec format matches the host OS".** The in-process runner COMPILES every declared target on every host (a cross-format emission regression must surface even on the wrong host, so the zero-diagnostic assert still applies there). It then SPAWNS only if (a) `runOn` names the current host OS, and (b) where the target's arch differs from the host's, the target declares an `emulator` that is on `PATH`. Missing either is a *named skip* in the arm ledger, never a pass: no `emulator` key is a manifest defect the corpus lint reds host-independently, and an absent emulator binary is a machine property that becomes a hard failure under `DSS_STRICT_ARM_VERDICTS=1`. The CLI runner instead binds exactly ONE target and ledgers the rest — **the candidate whose arch matches the host's own, else the first whose `runOn` names the host** (`selectBoundTargetIndex`, `tests/test_support/arm_verdict_ledger.hpp`). ⚠ It bound the plain FIRST match until 2026-08-17; if you are reading a row or a comment older than that, the arch preference is the part that changed.

★★ **THE COMPLEMENT, STATED AS A RULE RATHER THAN LEFT TO BE INFERRED — and it is MACHINE-CHECKED, so this paragraph does not have to stay right on its own.** For the target this host binds, BOTH runners compile it; for a `runOn`-excluded target, the **in-process runner is its ONLY compiler**. That boundary is asserted by the `integrated_tests/coverage-boundary` ctest entry, which drives both runners over one corpus example and judges five clauses — the two must read the same declared work, the CLI runner's coverage must NEST inside its sibling's, every declared spec must be compiled by SOMEBODY, neither runner may ATTEMPT to spawn a `runOn`-excluded spec, and the two must share an executed spec so the nesting clause compared something. The clauses forbid a LOSS of coverage and never a gain, so teaching the CLI runner to compile more leaves them green. ⚠ **Do not copy that entry's numbers into this file.** The boundary WIDTH is per-leg and per-corpus — the entry prints its own on whatever host runs it — and a figure pasted here is simply the next sentence to rot, which is a thing this file has now been measured doing twice.

The harness ASSERTS strictly: binary on disk, spawn success, no timeout, exit code `==` manifest value, and **zero ERROR-severity compile-time diagnostics unless the manifest declares `expectDiagnostics`** — <!--census:examples:top.expectDiagnostics-->44 examples do, and those invert the contract: the compile MUST fail with exactly the declared diagnostic set and nothing is spawned. Any drift breaks ctest. ⚠ **THIS SENTENCE USED TO SAY "zero compile-time diagnostics", and P54 (lane `fw`) made that false in two directions at once** — it was already false for the advisory warnings a `release` arm can emit (`examples/c/staticlib_alignas_carry` documents one it lives with), and it is now deliberately false for `expectWarnings`, the third thing a manifest can say: the compile SUCCEEDS, the artifact is still built and run and checked, **and** the named codes must have been emitted at Warning severity at the declared positions. That is the shape of every accept-and-report boundary the compiler has, and until this key no single entry could hold both halves of it — `examples/c/const_bitfield_write_warns` says so in its own manifest and splits its claim across two instruments for want of it.

**Top level**

- `language` — language name passed to `Program::compileFiles` (must match a `.lang.json` in `src/dss-config/sources/`). In PROJECT MODE the `.dss-project.json` is the authority and this is a MIRROR — both runners fail loud if the two disagree. *Declared by every manifest in the corpus.*
- `source` — the single source file name, relative to the example dir. <!--census:examples:top.source-->*919.*
- `sources` — a non-empty ARRAY of source file names, for a multi-CU example. An `expectDiagnostics` example must be single-source (one buffer, so a diagnostic's offset maps unambiguously). <!--census:examples:top.sources-->*32.*
- `project` — PROJECT MODE: the path (relative to the example dir) of a `.dss-project.json` that owns the build. The runners drive `Program::compileProject` / `dsscp --project` instead of `compileFiles` / `--compile`, which is the ONLY entry point that expands the manifest's source globs, runs its `preBuildScripts` / `postBuildScripts` hooks, and RESOLVES its `dependsOn` graph. <!--census:examples:top.project-->*6.* See **Project mode** below for the three things it changes.
- `exitCode` — exact OS exit code the spawned binary must produce. REQUIRED unless `expectDiagnostics` is present. <!--census:examples:top.exitCode-->*913.*
- `expectedStdout` — exact stdout the binary must print; declaring it is what routes the capture pipe. A per-target entry of the same name overrides it. *168 top-level + 78 per-target.*
- `expectDiagnostics` — a non-empty array of `{code, line, col}` (+ optional `positioned`) inverting the contract: the compile MUST fail, producing exactly this diagnostic set, and nothing is spawned. <!--census:examples:top.expectDiagnostics-->*44.*
- `expectWarnings` — the SAME entry shape, asserting the opposite verdict: the compile SUCCEEDS, the artifact is built, spawned and checked exactly as any other entry's, **and** every declared code was emitted at **Warning** severity at the declared position. REQUIRES `exitCode` (the program still runs) and is mutually exclusive with `expectDiagnostics` (an entry cannot be both a refusal and an accept-and-report) and with `project` (positions resolve against one named source buffer). ⚠ **The assertion is exact over the DECLARED CODES and silent about every other**, which is the one place it deliberately differs from `expectDiagnostics`' whole-set equality: a refused compile emits nothing incidental, a successful one can (an `X_OptFixpointTruncated` from a `release` arm), and an entry that reddened over an unrelated advisory would teach authors to stop declaring warnings at all. For each declared code, the set of positions it was emitted at must equal the declared set — a missing warning, a duplicated one and one that moved are all red. Added P54 (lane `fw`) for `S_FloatLiteralOverflowsToInfinity`. <!--census:examples:top.expectWarnings-->*16.*
- `optimizedPipelines` — extra ARMS of the same example, each re-compiled under a different optimizer pipeline and re-run against the same assertions. Each arm is `{"label": …}` plus EXACTLY ONE of `passes` (an inline array of `PassId` names) or `shippedPipeline` (a name under `src/dss-config/pipelines/` — `debug` or `release`). Both or neither fails loud. *✔Re-derived by `examples-census` and machine-checked by `.harness-config/runner/actions/check-doc-census/`: <!--census:examples:top.optimizedPipelines-->**814** carry the key, declaring <!--census:examples:arms-->**1046** arms — <!--census:examples:arms.shippedPipeline-->**723** name `shippedPipeline` and <!--census:examples:arms.passes-->**323** use an inline `passes` list.* An arm may also declare **`"mustDifferFromBaseline": true`**, which turns the image comparison from a report into an ASSERTION: the optimized artifact must not be byte-identical to the baseline's, and an arm that opts in and then produces an identical image is a hard red. *✔<!--census:examples:arms.mustDifferTrue-->**778** arms — plus <!--census:examples:dependsOn.mustDiffer-->**54** `dependsOn` entries, which carry the same key with per-dependency scope — declare it true and <!--census:examples:arms.mustDifferFalse-->**7** declare it false OUTRIGHT; the rest leave it absent. ⚠ An explicit `false` and an absent key are the SAME verdict — `OptimizedArm::mustDifferFromBaseline` defaults to `false` and the parse merely overwrites it with `false` — so both are report-only and the two spellings differ only in whether the author said so on purpose.* Declare it whenever the example has something the pipeline should visibly transform — without it an arm that silently stopped optimizing would still pass. ★ **A DECLARED ARM IS RUN, ATTEMPTED OR REFUSED — NEVER DROPPED.** An arm is compiled and run on the host where its target's baseline RUNS. On a target NO host runs (`runOn: []`) it is still **compiled — on every host, by the in-process runner — and its images judged** against the baseline's, so a `mustDifferFromBaseline` there bites like anywhere else; nothing is spawned. ⚠ Until P68 such an arm was ledgered `compile not attempted: baseline arm did not run` and built on no host at all — six manifests declared one — which is why older prose in this corpus says a build-only example "must not declare `optimizedPipelines`": that rule is retired. And `optimizedPipelines` beside `expectDiagnostics` is **refused at load by both parsers**: a refusal builds no image for an arm to differ from.

- `$comment` — the repo-wide config-documentation convention: provenance, what the example witnesses, the red-on-disable argument. Ignored by the runners. <!--census:examples:top.$comment-->*834.*

**EXACTLY ONE of `project` / `sources` / `source`.** All three answer the same question — *what does this example compile* — so declaring two is a hard parse error in BOTH runners, naming the pair. `sources` used to "take precedence over" `source`, which is the polite spelling of silently dropping one of them; zero manifests declare both, so the rule protected nothing and only stood ready to swallow a rename typo. `project` + `expectDiagnostics` is likewise rejected: the expect-error path needs one named source buffer and a project build has none — and since P54 `project` + `expectWarnings` is rejected for the identical reason, as is `expectDiagnostics` + `expectWarnings` (one entry cannot assert both that the compile was refused and that it succeeded).

**`targets[]` entries** *(<!--census:examples:targets-->3,244 across the corpus)*

- `spec` — the combined `<arch>:<object-format>` target spec. <!--census:examples:target.spec-->*3,244.*
- `artifact` — the produced binary's FILENAME (never a path — see **Project mode** for where a project build actually puts it). <!--census:examples:target.artifact-->*3,196.*
- `runOn` — host OS names (`windows` / `linux` / `darwin`) allowed to SPAWN this binary. <!--census:examples:target.runOn-->*3,196.* The same <!--census:examples:targets.noArtifactNoRunOn-->**48** target entries omit BOTH `artifact` and `runOn`, and ✔MEASURED every one of them sits in an `expectDiagnostics` manifest: they are the expect-error arms, which build nothing and spawn nothing. ⓘ <!--census:examples:targets.noArtifactNoRunOn-->48 target entries across <!--census:examples:manifests.noArtifactNoRunOn-->43 manifests — two such manifests declare two of them each, which is why these two figures are not the same number and never had to be. ✔The set equality above is re-measured, not inferred from the counts matching.
- `emulator` — the launcher to prefix when the target arch differs from the host arch, e.g. `qemu-aarch64`. Required for a cross-ARCH arm — see the run gate above. <!--census:examples:target.emulator-->*1,507.*
- `loaderSearchPathVariable` — the NAME of the environment variable through which this target's host LOADER accepts extra library directories (`LD_LIBRARY_PATH` on linux). When the target is spawned, BOTH runners set it — for that spawn alone, restored afterwards — to the directory of every library the build resolved against (each `dependsOn` artifact, each `prebuiltLibraries` file), ahead of any value it already had. It exists because DSS, like gcc and clang when no `-rpath` is asked for, records a dynamic library in DT_NEEDED by name with no DT_RUNPATH, so an ELF exec importing from a `.so` its own arm just built dies at exit 127 unless the loader is told where to look; on Windows the loader searches the executable's own directory unasked, so a pe64 arm never needs it. The runners know no loader and no variable — the manifest names one, the build supplies the directories (`tests/test_support/loader_search_path.hpp`). A declaration that could never act — on a `runOn: []` target, on a target that resolves against no library, or in an `expectDiagnostics` manifest — is **refused at load** by both parsers. The four dynamic-library examples (`dynlib_resolve_roundtrip`, `dynlib_literal_pool_roundtrip`, `preemptible_definition_address_in_shared_object`, `two_dynlibs_distinct_identity`) declare it on their ELF arms, which RUN on linux because of it; their Mach-O arms stay build-only until a Mac measures the same key with `DYLD_LIBRARY_PATH`.
- `runpaths` — directories this target's IMAGE records for its own loader to search for the libraries it needs (DT_RUNPATH on ELF, LC_RPATH on Mach-O), passed through verbatim and in order: one `--rpath <entry>` per entry by the CLI runner, `Program::setRunpaths` in-process. A leading `${ORIGIN}` is DSS's portable token for the directory of the image that carries the path, which each format's document spells its own way (`$ORIGIN`, `@loader_path`). Unlike `loaderSearchPathVariable`, which the RUNNER sets for one spawn, this is a property of the image — an arm that declares it runs with NO loader variable, which is the whole witness of `dynlib_runpath_origin`, whose control `dynlib_runpath_absent_exits_127` is the same program without it (exit 127). Must be a NON-EMPTY array of non-empty strings (the CLI refuses an empty `--rpath`, so an empty entry would make the runners build different things), and is **refused at load** beside `expectDiagnostics` by both parsers (a refusal links no image). A format that records no runpath (pe64) accepts the request with the `K_FormatLacksRunpath` warning. D-LK-IMAGE-CANNOT-DECLARE-A-RUNPATH.
- `exitCode` / `expectedStdout` — per-target OVERRIDES of the manifest-level pin, for a source whose observable is legitimately platform-divergent (e.g. `sizeof(wchar_t)`). *30 / 78.*
- `dependsOn` — prerequisite artifacts built FIRST and threaded into this target's `--resolve-library` (a static library the example links against). Each entry is `{sources, spec, artifact}`, optionally `multiCu` (accepted, unused by the corpus today), and may carry its OWN nested `dependsOn`, so a fat archive can merge an input archive. *<!--census:examples:target.dependsOn-->62 target entries across <!--census:examples:dependsOn.manifests-->15 manifests; <!--census:examples:dependsOn.entries-->70 dependency entries in all, <!--census:examples:dependsOn.nested-->4 of them nested — and <!--census:examples:dependsOn.mustDiffer-->54 i.e. every one, declare `mustDifferFromBaseline`.* ⚠ **THESE FOUR WERE HAND-MAINTAINED PROSE AND WENT FALSE SILENTLY** — they read "18 target entries across 4 manifests; 22 dependency entries … all 22" while the census already measured 26 / 5 / 26 / 26, so the sentence was stale by a whole example before this one landed, sitting three lines under a paragraph explaining that exactly this happens. They carry census markers now, so `doc_census_guard` compares them like every other figure instead of trusting the prose. ★ **EVERY PREREQUISITE IS BUILT UNDER THE ARM'S OWN OPTIMIZER CONFIGURATION**, nested ones included — a `release` arm compiles the static libraries through the release pipeline as well as the executable. Both runners used to build every prerequisite at the default no matter which arm asked, so a `release` arm here optimized the EXECUTABLE and left the libraries — the subject of the example — on the baseline pipeline, and passed anyway. A `dependsOn` entry may therefore carry its own **`"mustDifferFromBaseline": true`**, asserting that THAT prerequisite's image differs between the arm and the baseline. Prefer it to relying on the executable-level assertion: the exec differs for its own reasons too, so only the per-dependency form actually says the library was optimized. ★ **This is NOT the compiler's `dependsOn` — see below.**
- `$comment` — same documentation convention as at the top level, scoped to one target. <!--census:examples:target.$comment-->*11.*
- `prebuiltLibraries` — archives the corpus links against that **THIS REPOSITORY DID NOT BUILD**, threaded into the same `--resolve-library` set as `dependsOn` artifacts and AHEAD of them. Each entry is `{"path": <repo-root-relative>, "containerWitness": <ASCII token that must appear in the file's bytes>}`, and the key set is CLOSED. *2 entries in 1 manifest.* ★★ **THE `containerWitness` IS THE POINT OF THE KEY, NOT DECORATION.** A prebuilt fixture is the one input a corpus example cannot regenerate, so the failure mode is a file that is present but is no longer the thing the example meant — a stale checkout, a truncated copy, an archive rebuilt in a different flavour. The witness makes the manifest state what the bytes must contain (`__.SYMDEF` for a plain BSD archive, `__.SYMDEF SORTED` for Apple's), and a miss is a HARD FAILURE naming the resolved path — never a skip, because a skipped fixture check reads exactly like a passing one. ★ Why this exists at all: every `dependsOn` entry hard-requires a non-empty `sources` list, so before this key the corpus could not express *“consume an archive built elsewhere”* and a shipped capability had no runnable example ([[D-FF1-AR-BSD-CORPUS-EXAMPLE-NEEDS-A-PREBUILT-ARCHIVE-KEY-IN-BOTH-RUNNERS]]). ⚠ An ABSENT key fires no call site at all, which is what lets the other 633 manifests build byte-unchanged. ★ **This is NOT the harness `dependsOn` and not the compiler's** — a third staging path, and the only one whose input is outside the build graph entirely.

★ **THE `dependsOn` ABOVE IS THE HARNESS'S, AND THERE IS A SECOND KEY OF THE SAME NAME THAT IS A DIFFERENT FEATURE.** The one documented here lives in `expected.json`, is read by the two corpus runners, and builds a **test FIXTURE**: a prerequisite artifact the runner stages so an arm has something to compile against. The compiler's `dependsOn` lives in a user's `.dss-project.json`, is read by the project-config loader, and is a **PRODUCT feature** — a real dependency-resolution surface with a `.dss-deps` cache, a composition-verb dispatch and its own diagnostic band ([`docs/project-config-spec.md` §2.6](../docs/project-config-spec.md)). Two files, two loaders, two audiences.

**They COEXIST deliberately, and the reason is INDEPENDENCE.** If the corpus's fixture staging went through the compiler's resolver, a resolver bug would turn examples red that have nothing to do with dependencies — and the corpus would lose the one staging path that does **not** depend on the feature under test. A harness that cannot build its own fixtures without the feature it is testing has no independent verdict left to give. A rename was considered and **REJECTED** (operator, 2026-08-12): the harness key was measured first — it appears in exactly the two manifests counted above, so renaming it would have been cheap, and renaming the *product* key instead was priced across loader, tests, spec, plan and the `D_Dependency*` code names. The call was **neither**; both keep the name, and the distinction is carried by **documentation alone** — this paragraph and its twin in the project-config spec. That is why it is written down rather than left to be re-derived: **an undocumented duplicate name is how the wrong one gets deleted.** Do not re-propose the rename, and do not "unify" the two.

## Project mode

`"project": "<file>.dss-project.json"` replaces `source`/`sources`. The example dir then ships the project manifest, plus whatever that manifest's own `sources`, hooks and dependencies need. Four examples use it today, one per capability the mode unlocks:

- **`project_prebuild_script_codegen`** — build-lifecycle hooks. Its `preBuildScripts` hook GENERATES the C source; the manifest's `sources` is the pattern `generated_*.c` and matches nothing until the hook has run, so a green run witnesses the entire chain — script spawn → file written → glob expanded → compile → link → spawn → exit 42.
- **`project_dependson_module_source_merge`** — the compiler's `dependsOn`, `SourceMerge` arm. `scalemod/` is a nested project declaring `"artifactProfile": "module"`; its sources are MERGED into this compilation, and `main.c` calls a function only that module defines.
- **`project_dependson_staticlib_artifact_link`** — the compiler's `dependsOn`, `ArtifactLink` arm. `foldlib/` declares `"artifactProfile": "staticlib"`, so it is BUILT to its own archive under `<output>/deps/foldlib/<formatName>/` and threaded into the consumer's `resolveLibraries`. Its own `targets[]` lists one ELF spec while the consumer builds four targets — deliberately, because a dependency's `targets[]` is not consulted when it is built as a dependency.

- **`project_module_standalone_build`** — `artifactProfile: "module"` built STANDALONE, with no consumer anywhere in the example. Plan 06 §5.1 B.13.3 ruled that a module IS a library (served by every format that serves `lib`/`staticlib`), so a module project emits a real archive of its own; before that ruling this build was REJECTED at the AP3 profile-vs-format gate, and a module's own errors were undiscoverable until some consumer imported it. It is the corpus's cross-leg half of a capability whose `!<arch>` magic-byte check lives in the unit pin `ModuleIsALibrary.StandaloneModuleBuildEmitsAnArchive` — deliberately the only assertion split of its kind here, because neither runner can assert artifact CONTENT. ★ It is also the corpus's second all-`runOn: []` manifest; see the divergence note above for what that costs it.

Both `dependson` examples take a **`path`** dependency only. No corpus example may reach the network.

```json
{
  "language": "c",
  "project": ".dss-project.json",
  "exitCode": 42,
  "targets": [
    { "spec": "x86_64:pe64-x86_64-windows-exec", "artifact": "prebuild_codegen.exe", "runOn": ["windows"] }
  ]
}
```

Three things differ from a `--compile` example, and both runners implement all three identically:

1. **The project manifest's `targets[]` is the build authority; the per-target `spec` is a MIRROR.** `Program::compileProject` takes no targets argument, so `spec` cannot drive a project build — it selects which of the project's own targets this arm runs, gates `runOn`/`emulator`, and names the artifact subdirectory. Each runner cross-checks it against the project manifest's `targets[]` and fails loud on a miss, so a stale mirror is caught at the mirror rather than surfacing later as a missing artifact. (One project manifest lists every target; the alternative — one manifest per corpus target — would make an example ship N near-identical copies of a user-facing file to work around a harness limitation.)
2. **The artifact is under a per-format subdirectory.** A project build forces `setPerFormatOutputSubdir(true)`, so it lands at `<outDir>/<formatName>/<artifactName-or-stem><ext>` even for a single target. `artifact` still names the FILE; the runners compose the subdirectory from `spec`. Do not spell the subdirectory into `artifact` — it would make one key mean two things.
3. **The COMPILE runs with the example's staged directory as the working directory** (the in-process runner's `ScratchDir::useAsCwd()`; the CLI runner's `CwdGuard`, which wraps the project-mode compile as well as the RUN). Since 2026-09-21 that is no longer what decides which files a project build reads: every relative path in a `.dss-project.json` — its `sources[]` and their globs, `includes`, `resolveLibraries`, `output`, and the directory and program of a generator script — resolves against **that manifest's own directory**, from wherever the build starts (`docs/project-config-spec.md` §2.2). A staged project therefore means the same files under both runners by construction, and a nested `dependsOn` project means the files beside its own manifest.

A declared build script whose interpreter is absent from the machine is ledgered `skipped-build-input-missing` — an ENVIRONMENTAL skip, warned by default and a hard failure under `DSS_STRICT_ARM_VERDICTS=1`. Everything else in project mode (a missing project manifest, a spec the project does not build, a language mirror that disagrees, a failed compile, a missing artifact) is a hard runner failure, never a skip.

⚠ **Where the two runners currently diverge:** `project` is read by BOTH, with the same validation, the same skip vocabulary and the same artifact-path rule — that is the rule working, and it is what lets the project-mode examples above (including their nested `dependsOn` trees) assert on both surfaces.
